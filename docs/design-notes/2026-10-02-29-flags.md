# Design note 29: ambiguity and duplicate flags on Shape, 2026-10-02

Story E4-4, on the Shape page of E4-2 and E4-3. The PM app board (PmApp.dc.html, Shape)
draws one ambiguity banner above the areas in the unclear tint with a Dismiss pill; this
build stacks one banner per flagged item and adds the duplicate banner the story asks for.
Screenshot beside the boards: shape-flags-desktop.png.

## The banners

Above the areas, one per flagged item in position order, the Banner of the design system
(unclear tint, unclear text, a white Dismiss pill with the lilac border): "Ambiguity in
[REF]. [What the item does not say]. Respondents may mark it unclear." and "[REF] may
duplicate [REF]. If they ask for the same thing, remove one in the file and import it
again." Each ref is a link to the item's row. The row carries the same note in 12 px under
its text: "Ambiguity: ..." or "May duplicate [REF]." Refs are the source reference when the
import had one, else the position.

## Decisions taken here

- The flags are the model's (E4-2 stores them on the item at each run), validated by the
  schema and the checks: an ambiguity is a string up to 300 characters, a duplicateOf must
  name an earlier item of the set or it is dropped at the run; flagsFor() drops a duplicate
  whose target is no longer in the set before display (acceptance 4).
- Dismiss sets flags.dismissed on the item and hides both of its banners and its note. A
  re-run keeps the dismissal whatever the model says next (acceptance 3): the model's new
  text is stored, the banner stays hidden. Dismissal is per item, not per wording; a PM who
  wants to see a later flag on that item cannot. Recorded as a known limit (note 27 raised
  it); a flag that reappears when the wording changes is a possible R2 refinement.
- Dismiss is the only action, as the story says for R1: merging is a re-import.
- The sample project shows no banners (its seed carries no flags); the banners it would
  show are read-only there.
