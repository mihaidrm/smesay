# Design note 52: autosave and resume, 2026-10-04

Made in the Claude Code cloud session of 2026-10-04 for stories/E7-3, under decision 0044.

## What was decided

- Every answer the server has not confirmed stays in the page and in localStorage under
  smesay-answers:[token], tied to the response, until the server holds it. Opening the link
  again shows on the cards whatever is there for that response that differs from the
  server's answer, and sends it with the version, page and number it was queued with, so
  the server's rule below decides, as it would have for the closed page (the fourth audit:
  judging on the page from the version alone dropped a change made after the closed page's
  own earlier save). When the server answers that another window or device changed it, the
  card shows the stored answer with the sentence. A second window on the link keeps its own
  entries in the same store (read, change, write).
  A closed, revoked or unknown link's page removes the store for that link.
- The server counts each answer's writes (answer.version) and keeps which open page wrote
  it last (writer, a random id per page load) with that page's number for the save
  (writer_seq). Every change carries the version it was made on, the page and its number.
  The server stores a write when the stored version is still the one it was made on, or
  when the same page wrote last with a lower number (its earlier save landed but the reply
  was lost), or when the change names the last write as one it was made on top of;
  otherwise it answers "stale" with the stored answer. A change names saves of other pages
  (after) when it was made on a card whose change from another page still waited for the
  server, typically one the device kept from an earlier visit: it keeps that change's
  version and lands only where that change would have (the fifth audit: taking the version
  the page had loaded let such an edit replace another device's answer when the kept
  change's request was lost). So a late request,
  another window or a queue left on another device never replaces an answer saved since
  (the audits' blocking finding). Two tries came first: a count of the page's own changes,
  which let a long offline edit outrank a later short one (second audit), then the
  respondent's edit time, which needed the device's clock and could not confirm the page's
  own save once a clock running ahead was corrected (third audit). No clock decides now. A
  stale reply written by the page itself, by a kept change's page with exactly that save, or
  saying what the page sent, changes nothing (a later save of the kept change's page is
  another tab's newer change, sixth audit);
  any other came from elsewhere, and the card shows the stored answer with a sentence that
  says to change it again if theirs should stand. A newer change of the page waiting behind
  that save was made on the old answer too and is dropped with it.
- Every write names the response the page answers for; a write for a response that is not
  the device's is "not started", so an open window never writes into a response started
  since in another window.
- A change is sent 400 ms after the last keystroke and never more than 900 ms after the
  first change still waiting, so steady typing still saves within a second. A request with
  no answer in 10 seconds is given up and counts as offline.
- A request that cannot reach the server turns the header note to "Not saved" and shows the
  connection banner over the chapter. The page asks the state route every 5 seconds, and at
  once when the browser reports it is online; the first answer sends every waiting answer.
  A server failure (5xx), a rate limit or any unexpected code retries the same way with
  "Not saved" and no banner, since the connection is not the cause; "Not saved" stays until
  every failed answer has gone through. A send as the page hides that fails counts the same,
  and when the page shows again what is unconfirmed goes out. A complete card not yet on the server reads "Not saved yet" (the
  respondent board). Of the failures only a 422 drops an answer; a stale reply from another
  window or device drops the change too, with the sentence.
- A browser that refuses localStorage gets the notice once, over the first screen it shows
  after About you, and works in one sitting. A private window's storage is cleared when its last
  private tab closes (MDN, Window.localStorage); those windows get no notice. A browser
  that blocks cookies usually blocks storage too (the same page, Exceptions): Start works,
  the first save finds no response, and the note under Start says the cookie was not kept.
- A returning visit with no screen in the address lands on the first chapter with an
  unfinished item, on that item in the one-item layout; when everything is complete, the
  Wrap up (E7-4, which also adds "Welcome back").
- The "newer version" page is not built: publishing a newer version closes the older links,
  so a respondent mid-way sees the closed page and nothing points to the new link
  (docs/review-list.md).

## Checks

- src/lib/answer-queue.test.ts: restore this response's entries that differ from the
  server's answer with their version, page and number; malformed storage and versions,
  pages or numbers out of range; two windows; removal by page and number; moving a waiting
  change on top of its own save; removal of one response's queue; the timing; an edit on top
  of another page's kept change (nextEntry); own writes against another tab's (ownWrite: a
  later save of the kept change's page is not this page's); what each reply does to the
  queue (replyStep); the outcome of each status.
- src/lib/respondent.test.ts: resumeAt; the post's version, page, number and after; a write
  on an older version from another page, or an earlier number of the same page, is stale and
  changes nothing, a later number of the same page lands; a write naming the stored save in
  after lands, one naming an earlier save of a page that wrote again is stale; the route's
  409 stale; the answers route after a revoke answers 410 and writes nothing.
- e2e/respondent-autosave.spec.ts: pick to request under a second; offline, two answers,
  back online, both Saved, a complete card "Not saved yet" while offline; an answer left
  offline in a closed tab sent on the next visit; the landing chapter; a change kept unsent
  in one browser dropped, with the sentence on its card, after a second browser with the
  same device cookie saved the answer; localStorage blocked.

## What was not decided

- Hours offline: the queue is per tab and per device, not a service worker (the story's out
  of scope).
