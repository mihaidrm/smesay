# Design note 27: Shape, the areas and the moves, 2026-10-02

Story E4-2, the first screen of the Shape step. The PM app board (PmApp.dc.html, Shape)
draws the areas with their rationale and the items with reader versions and Accept and
Reject; this story builds the areas and the moves, E4-3 adds the reader versions and the
buttons, E4-4 the flag banners, E4-5 the context line. Screenshot beside the boards:
shape-desktop.png (after a run, the fake model's answer).

## The page

Title "Shape the list" with the one button on the right: "Shape with AI" (primary) before the
first run, "Run again" (secondary) after. Under the title, before a run, the intro sentence;
after a run, "AI grouped 6 items into 3 areas." with the run-again hint in 13 px. Then one
section per area in the model's order: a grey-50 header with the name and the rationale,
rows of ref (mono, muted), the original text at 15 px, the pills ("Placed by AI", "Moved by
you") and, after a run, a "Move to" select with a Move button. Before a run the list is
read-only: the imported areas as sections, or "Not shaped yet" with every item. A refusal
from the model shows beside the button in the unclear tint with "Try again".

## Decisions taken here

- Drag and drop is the browser's own (HTML Drag and Drop API), no library. The research
  check: @dnd-kit/core 6.3.1 (MIT) was last released 2024-12-05 and its repository shows
  88 open issues; @dnd-kit/react 0.5.0 (MIT, 2026-09-12) is before 1.0. Neither is worth a
  dependency for one list. The keyboard path the story asks for is the "Move to" select and
  button on every row, which the browser test uses; dragging calls the same server action.
  Mihai can overturn this for a library when E5's builder needs richer reordering.
- The model's answer is the whole shaping output (areas, reader versions, flags) in one
  call, so E4-3 and E4-4 show what is already stored instead of calling again. Reader
  versions are stored as "suggested" and flags as the model gave them; the page shows
  neither yet.
- Refs in the prompt are the item positions ("[4]"), not the source references, which a
  pasted list lacks and a spreadsheet can repeat. The reader never sees them: the row shows
  the source reference when there is one, else the position.
- The area order and the run count live on the item set (area_order, shape_runs, shaped_at,
  migration 0010); the rationale on each item of the area, as the story's notes say.
- On a re-run, an item the model placed on an earlier run is sent without an area, so it is
  placed again; an item the PM moved keeps its area and gets the area's new rationale. An
  item without an area column anywhere stays unmarked: the "Placed by AI" pill means the
  import had areas and this item none.
- The checks on top of the schema (every item in exactly one area, no unknown ref, imported
  names unchanged, 3 to 8 areas otherwise) are in checkShape and reach the log as counts.
  The golden set's own expectation for spec 01 passes the partition check (acceptance 1).
- The browser test runs against a stand-in for the API (e2e/fake-anthropic.mjs, started by
  Playwright as a second web server) that keeps the imported areas and puts the loose items
  in the first one, so the test can assert the moves and the re-run without a model.
