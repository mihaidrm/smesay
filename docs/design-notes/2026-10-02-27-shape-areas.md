# Design note 27: Shape, the areas and the moves, 2026-10-02

Story E4-2, the first screen of the Shape step. The PM app board (PmApp.dc.html, Shape)
draws the areas with their rationale and the items with reader versions and Accept and
Reject; this story builds the areas and the moves, E4-3 adds the reader versions and the
buttons, E4-4 the flag banners, E4-5 the context line. Screenshot beside the boards:
shape-desktop.png (after a run, the fake model's answer).

## The page

Title "Shape the list" with the one button on the right: "Shape with AI" (primary) before the
first run, "Run again" (secondary) after. Under the title, before a run, the intro sentence;
after a run, "AI grouped 6 items into 3 areas." with the run-again hint in 13 px. Then one
section per area in the model's order: a grey-50 header with the name and the rationale,
rows of ref (mono, muted), the original text at 15 px, the pills ("Placed by AI", "Moved by
you") and, after a run, a "Move to" select with a Move button. Before a run the list is
read-only: the imported areas as sections, or "Not shaped yet" with every item. A refusal
from the model shows beside the button in the unclear tint with "Try again".

## Decisions taken here

- Drag and drop is the browser's own (HTML Drag and Drop API), no library, which departs from
  the story's technical note ("a keyboard-accessible library"); the story now says so and the
  choice is Mihai's to overturn (see Open for Mihai). The research check, read 2026-10-02
  from the npm registry (`npm view`) and the repository page github.com/clauderic/dnd-kit:
  @dnd-kit/core 6.3.1 (MIT) was last released 2024-12-05 and the repository shows 88 open
  issues; @dnd-kit/react 0.5.0 (MIT, 2026-09-12) is before 1.0. The keyboard path the story
  asks for is the "Move to" select and button on every row, which the browser test uses;
  dragging calls the same server action.
- The model's answer is the whole shaping output (areas, reader versions, flags) in one
  call, so E4-3 and E4-4 show what is already stored instead of calling again. Reader
  versions are stored as "suggested" and flags as the model gave them; the page shows
  neither yet.
- Refs in the prompt are the item positions ("[4]"), not the source references, which a
  pasted list lacks and a spreadsheet can repeat. The reader never sees them: the row shows
  the source reference when there is one, else the position.
- The areas in order, each with its rationale, and the run count live on the item set
  (areas, shape_runs, shaped_at, migration 0010); each item also carries its area's
  rationale, as the story's notes say, for the respondent side.
- Who put an item in its area is one flag, item.flags.areaBy: "ai", "pm", or absent for an
  area that came with the import; the first run also writes flags.importedArea on every item
  that came with one, so a move never loses where it came from. On a re-run an "ai" item is
  sent without an area and placed again (so a list without an area column can be regrouped,
  the audit's first finding); a "pm" item is sent as "(keep in: name)", which is not an
  imported area: the model must name that area and keep the item in it, and may regroup the
  rest; an imported item is sent with its area and the answer is refused if the model moved
  it (the audit's third finding). The "Placed by AI" pill is "ai" on a set whose import had
  areas.
- The imported area names are data: they go in the user message under AREAS, never in the
  system prompt (the audit's second finding).
- The areas with their rationale live on the set (item_set.areas), so an area the PM empties
  keeps its rationale and its place until the next run; each item also carries its area's
  rationale for the respondent side.
- The checks on top of the schema (every item in exactly one area, no unknown ref, names
  trimmed and distinct, imported names and placements unchanged, 3 to 8 areas otherwise) are
  in checkShape and reach the log as counts. A duplicateOf flag that names an unknown ref, the
  item itself or a later item is dropped, not refused (E4-4, acceptance 4). The golden set's
  own expectation for spec 01 passes the partition check (acceptance 1).
- Ceilings before a call: 12 imported areas and 60 characters per name (the schema's limits,
  which the model could not meet), and 400 items, an estimate of what one answer carries in
  E4-1's 16,000 output tokens at about 40 tokens per item (unverified until E4-6 runs the
  real model), and a prompt over E4-1's 500,000 characters. Each has its message; none gets
  a Try again button. "Try again" shows only
  when the AI did not answer or answered badly.
- A move to the area an item is already in changes nothing. Moves wait for the first run.
- The browser test runs against a stand-in for the API (e2e/fake-anthropic.mjs, started by
  Playwright as a second web server) that keeps the imported areas and puts the loose items
  in the first one, so the test can assert the moves and the re-run without a model. The app
  server is never reused by Playwright, so a dev server with the real key cannot be hit.
- The stepper's current step is a link when its page exists: Shape is current from the
  import on and this pill is the way in (the audit's fourth finding; MISTAKES.md).

## Known limits, left as they are

- Two shaping runs, or a run and a move, are serialised by the row locks (both read their
  rows for update); the budget check before the call is E4-1's read-then-call. A move checks
  its target area before it takes the lock, so a run that commits in that instant and drops
  the area leaves the item in an area the set no longer lists, until the next move or run.
- A dismissed flag (E4-4) is kept across runs at item level, so a different ambiguity raised
  later arrives dismissed too. E4-4 decides whether dismissal remembers the text.
- "Saved within one second" (acceptance 3) is not measured; the move is one server action
  and a page refresh.

## Open for Mihai

- The golden set and this story disagree. checkShape refuses an answer that drops or merges
  an item ("every item in exactly one area"), and the prompt forbids it. The golden set
  expects noise rows dropped (spec 07's bug rows and the Won't do row, spec 01's meeting
  notes) and allows duplicates merged (specs 01 and 08), and spec 05 is prose with no list.
  Fed as imported rows, those specs can only fail E4-6's "invented item" rule. Recommended:
  shaping never drops an item (the PM deletes rows in the file; E3-5 folds exact duplicates),
  and E4-6 scores the specs as imported rows, with the "not items" rows removed from the
  expectation files. Your call before E4-6.
- No library for drag and drop (above). Say so if you want dnd-kit or another when E5's
  builder needs reordering.
- The 400 item ceiling. Lifting it means chunking the list into several calls (areas across
  chunks are then a second pass). Recommended after E4-6 shows real token counts.
- "Continue" to Build is not on the page until E5-1 exists; the stepper stays on Shape.
- The Shape copy (docs/copy/app.md, Shape) and the seven Shaping rows in errors.md are new
  and wait for your acceptance.
