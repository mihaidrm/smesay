# Design note 88: an admin's view of a workspace, 2026-10-05

Made in the Claude Code cloud session of 2026-10-05 for stories/E14-4, under decision 0044.

## What was decided

- The view lives on the admin's session row (view_as_workspace_id, view_as_until), better-auth
  additional fields beside current_workspace_id, written through the same adapter. It counts
  only while the session's email is in ADMIN_EMAILS and verified, the 60 minutes have not run
  out, and the workspace is not marked deleted. Otherwise the next request writes view_stopped
  with the reason (expired or ended) and then clears it; an email no longer an admin's is
  cleared with no row, as there is no admin to record it under. A new start stops the view
  held first, so every start has its stop. A view ended by signing out (the session row goes)
  writes no stop row; the start row and the 60 minutes bound it.
- getAppContext serves the viewed workspace as the current one and the only one listed, so
  every page, the sidebar and the respondent preview show what the owner sees. Settings is
  drawn as an owner sees it.
- One helper for writes: every server action of the PM app takes its workspace from
  requireWritableWorkspace, and the three that work without one (create, switch, leave a
  deleted workspace) call refuseWhileViewing. During a view both send the request to
  /app/view-only, which says "You are viewing as [WORKSPACE]. Changes are off." A redirect is
  the one answer every action shape shares: the actions return different states, and a thrown
  error would reach the error page with its text hidden in production. The two export routes
  (they write the export log) take the same helper, and their download links are drawn and
  act disabled in the view. A unit test splits every server action file into its top-level
  declarations and fails when an exported action's first awaited call (after the session check)
  is not the helper or a local function whose own first call is; it also fails on a route that
  reads the workspace without the helper, but the live updates stream.
- Writes made while drawing a page are stopped where they happen: Build does not create the
  first instrument during a view (it says the owner has not opened Build yet), the sample's
  sample_opened event is not written, the quickstart is neither shown nor stamped (an admin
  can also be a member of the workspace), and the Plausible script is left out. /app/switch
  goes back to the viewed workspace.
- What the owner sees: Results reads the first owner's choices (tiles, view, the unsubmitted
  switch), so the counts match the owner's screen; Settings draws no "you" row; Shape's drag
  and drop and reader controls are read-only.
- The page itself: a violet banner across the top of the content with the workspace, the end
  time in UTC and Stop viewing; the content sits in a disabled fieldset, so every button and
  field below is disabled (the buttons and the segmented control at 40 percent, the fields at
  the 50 percent the design system gives them) while links still lead everywhere. The sidebar stays usable: its links, the mode
  toggle, Sign out.
- Stop viewing goes back to the workspace's admin page. Starting and stopping are audit rows.

## Why

Story E14-4 asks for the exact screen a PM describes, with nothing changeable and a trace.

## Rejected

- A separate "view" session or cookie: the story's technical note puts the state on the
  admin's session row, and one session keeps sign-out simple.
- Hiding the buttons: the story asks to show them disabled, so the admin sees what exists.
- Filters and tabs that are buttons are disabled too (they are form controls); the admin moves
  between pages and tabs through links.
